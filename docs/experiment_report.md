# Отчет об эксперименте: Потоковая обработка данных из Common Crawl без записи на диск

## 1. Постановка задачи
В рамках разработки пайплайна обработки данных перед нами стояла задача:
* Обработать распределенный архив из публичного репозитория **Common Crawl** (`commoncrawl`).
* **Ограничение №1 (Extra Credit):** Не скачивать промежуточные `.gz` файлы на жесткий диск, выполняя загрузку и распаковку **исключительно в оперативной памяти** (`BytesIO`).
* **Ограничение №2:** Не загружать весь целевой файл целиком в память, а производить его **потоковое (строчное) чтение** в `stdout`.
* Извлечь первый элемент индекса (URI) из корневого архива (`wet.paths.gz`), скачать по нему целевой архив (`.warc.wet.gz`), распаковать его «на лету» и вывести данные наружу с минимальным потреблением ресурсов.

---

## 2. Что мы сделали
Для реализации эксперимента мы выстроили модульную архитектуру и собрали скрипт сквозного пайплайна:
1. **HTTP/CloudFront загрузчик в память:** Написали функцию потоковой загрузки через `requests` с разбиением на чанки (`chunk_size=8192`), направляя байты напрямую в буфер оперативной памяти (`io.BytesIO`).
2. **Инкапсуляция распаковки (`GzipExtractor`):** Расширили наш класс распаковки GZ-архивов, добавив статический метод для распаковки потоков в памяти без обращения к файловой системе.
3. **Универсальная читалка (`LineReader`):** Реализовали режим получения первой строки в переменную (`mode="variable"`) для извлечения URI и потоковый режим (`mode="stdout"`) для вывода строк.
4. **Профилирование памяти (`memory_profiler`):** Обернули весь пайплайн в контекстный менеджер на базе встроенного модуля `tracemalloc`, чтобы в реальном времени фиксировать пиковое (`Peak`) потребление RAM.
5. **Интеграция в CLI:** Добавили запуск эксперимента в наш командный интерфейс в виде подкоманды `experiment`.

## 3. Чему научились: Роль и применение статических методов (`@staticmethod`)

В процессе реализации распаковки в памяти (`GzipExtractor.decompress_to_memory`) мы столкнулись с классическим архитектурным вопросом: *когда делать метод статическим?*

* **Что такое статический метод:** Это метод внутри класса, который не принимает ссылки на экземпляр класса (`self`) или сам класс (`cls`). По сути, это обычная функция, логически сгруппированная внутри пространства имен класса из-за схожести решаемых задач.
* **Почему в нашем случае `@staticmethod` оказался идеальным выбором:**
  * **Отсутствие состояния (Stateless):** Распаковка `BytesIO` буфера не зависит от внутренних полей конкретного экземпляра `GzipExtractor` (у него нет атрибутов вроде `source_dir` или `target_dir` для этого метода). Данные полностью передаются через аргументы и возвращаются наружу.
  * **Чистота и удобство вызова:** Нам не нужно инициализировать объект класса (`extractor = GzipExtractor()`), чтобы вызвать операцию. Мы можем вызвать её напрямую как утилиту: `GzipExtractor.decompress_to_memory(buffer)`.
  * **Архитектурная чистота:** Метод четко отделяет операции, привязанные к файловой системе диска (которые могут требовать состояния), от чистых неизменяемых преобразований потоков в оперативной памяти.
